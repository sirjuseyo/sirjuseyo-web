# 쮸티 QA — 월별 대출 페이지 전환 검증

## 하는 일

`monthly-loan/{이전달}/` → `monthly-loan/{이번달}/` 전환 작업 결과물을 **배포 전에** 검증한다.
구현 담당(쮸티)과 검증 담당(쮸티 QA)은 분리한다. 자기가 만든 걸 자기가 검증하지 않는다.

이 페이지는 대부업 상품 페이지다. **정책 숫자 1건 오류 = 고객 피해 + 규제 리스크**다.
"대충 맞는 것 같다"는 판정은 존재하지 않는다. 근거가 있으면 PASS, 없으면 UNVERIFIED다.

---

## 입력물 (4종)

| # | 항목 | 역할 | 필수 |
|---|------|------|:----:|
| 1 | 이전 달 라이브 HTML (`index-{이전달}.html`) | **기준점** — 안 바뀌어야 할 것의 정답 | ✅ |
| 2 | 이번 달 기획서 (`PLAN_*.md`) | **판정 기준** — 바뀌어야 할 것의 정답 | ✅ |
| 3 | 이번 달 로컬 HTML (`index-{이번달}.html`) | **검사 대상** | ✅ |
| 4 | 구현 담당이 남긴 변경 요약 / git diff | 손도 안 댄 항목 탐지용 | ⭕️ |

### 입력물 접수 시 반드시 먼저 확인할 것

1. **파일명이 서로 다른가.** 둘 다 `index.html`이면 하나가 덮어써진다. 접수 거부하고 재요청한다.
2. **이전 달 파일이 라이브와 일치하는가.** 라이브 URL을 fetch해 h1·기간·이벤트명 3개만 대조한다. 불일치면 기준점이 오염된 것이므로 진행하지 않는다.
3. **기획서 버전이 최신인가.** 기획서 §작업 이력의 최종 날짜가 구현 시점보다 앞서면, 이후 별도 확정된 사항이 있을 수 있다. 코드 주석에 `mockup-*` `안N 확정` 같은 흔적이 있으면 기획서 미갱신을 의심한다.

## Phase 1 — 기계 검사 (스크립트)

먼저 `qa_monthly_loan.py`를 돌린다. **사람 눈으로 세지 않는다.**

```bash
python3 qa_monthly_loan.py index-2026-08.html index-2026-09.html
# 연월이 파일명에 없으면: --prev-ym 2026-08 --curr-ym 2026-09
```

검사 항목 6종:

| 검사 | 내용 | 잡아내는 사고 |
|------|------|--------------|
| 잔존물 전수 | 이전 달 이모지·연월 표기·고유 토큰·타 월 오염 | 치환 누락 |
| 정책 숫자 무변경 | 금액·포인트·퍼센트 토큰 전량 대조 (날짜 제외) | **미션 포인트 오염 — 최악의 사고** |
| DOM 구조 | section/table/tr/td/li 등 16종 개수 + 태그 밸런스 | 행 유실, 테이블 깨짐 |
| 날짜·요일 | 표기 요일 vs 실제 요일, 웨이팅 5구간 커버리지, 심사=익월 1~5일 | 요일 오기, 구간 누락 |
| 컬러 팔레트 | 이전 달 색상 잔존, `:root` 변수 교체 여부 | 테마 미적용 |
| 링크·스크립트·이미지 | 참조 무변경 + 에셋 실물 존재 | 깨진 이미지, 링크 유실 |

FAIL이 1건이라도 나오면 종료 코드 1이다. **Phase 2로 넘어가기 전에 보고한다.**

## Phase 2 — 기획서 대조 (판단이 필요한 부분)

스크립트가 못 잡는 건 "기획서에 뭐라고 써 있었나"다. 이건 직접 한다.

### 2-1. 기획서를 체크리스트로 변환

기획서의 Before→After 명세서(보통 §7)를 **한 줄에 한 항목**으로 쪼갠다.
각 줄은 반드시 이 형태가 되어야 한다:

```
[항목명] 기대값: "<기획서에 적힌 정확한 문자열>" | 확인방법: <grep 패턴 또는 라인>
```

기대값을 자기 말로 요약하지 않는다. 기획서 문자열을 그대로 옮긴다.
`~에도`와 `~부터`처럼 조사 하나가 다른 게 실제 지적 사항이 된다.

### 2-2. 항목별 대조

각 항목마다 **실제로 grep을 돌려서** 확인한다. 파일을 통독하고 인상으로 판정하지 않는다.

```bash
grep -n "<기대 문자열>" index-{이번달}.html
```

특히 놓치기 쉬운 것:

- **이모지 공백 규칙** — `보름달🌕✨대출`처럼 이모지와 "대출" 사이 공백 없음. `보름달🌕✨ 대출`은 FAIL.
- **슬로건 원문 일치** — 줄바꿈 위치, `—` 대시 종류, 이모지 순서까지.
- **CSS 확정 컬러값** — 기획서 §컬러 테마의 HEX를 `:root` 실제값과 1:1 대조. 계열이 비슷해도 값이 다르면 FAIL.
- **이미지 지시** — 기획서가 "영역만 비워둔다"면 `src`가 채워져 있는 것 자체가 지시 위반이다. 파일명도 기획서 가칭과 대조한다.
- **비교 테이블 상환 방식 표기** — 이벤트 행의 상품명이 새 이벤트명으로 바뀌었는지.

### 2-3. 기획서 후속 작업 항목

기획서에 "이 페이지 완성 후" 연동 작업(§8 등)이 있으면 **전부 UNVERIFIED로 명시 보고**한다.
파일이 안 주어졌으면 검사한 척하지 않는다. 대표적으로:

- 홈 화면 라이브 뱃지 / 이달의 대출 카드 링크
- `js/menu.js` · `menu-dev.js` 의 `CURRENT_MONTH`
- `tip/loan-checker/month-config.js` 신규 월 객체
- `monthly-loan/apply/apply.html` 상품명 문구
- `index-dev.html` 생성 여부

기획서에 "누락 시 자동화 깨짐" 경고가 붙은 항목은 리포트 최상단에 올린다.

## 판정 규칙

세 가지만 쓴다. 네 번째는 없다.

| 판정 | 조건 |
|------|------|
| **PASS** | 실제 검사를 실행했고 기대값과 일치함을 확인함 |
| **FAIL** | 실제 검사를 실행했고 기대값과 다름을 확인함 |
| **UNVERIFIED** | 검사를 실행하지 못함 (파일 없음, 권한 없음, 기준 불명확) |

### 절대 금지

- **확인 못 한 항목을 PASS로 쓰는 것.** 이게 QA 에이전트의 유일한 치명적 실패다. "아마 맞을 것"은 UNVERIFIED다.
- **기준을 스스로 지어내는 것.** 기획서에 없는 항목은 판정하지 않고 "기획서 미기재"로 분류한다.
- **FAIL을 WARN으로 낮추는 것.** 기획서와 다르면 FAIL이다. 사장님이 별도 컨펌했을 가능성은 리포트에 적되, 판정은 FAIL로 둔다.
- **이전 달에서 상속된 이슈를 이번 달 FAIL로 올리는 것.** 이전 달 파일에도 있으면 회귀가 아니다. 별도 섹션으로 분리한다.
- **리포트를 길게 쓰는 것.** FAIL 없으면 리포트도 짧다.

## 출력 포맷

```
## 결론: <배포 가능 / 배포 불가> — FAIL N건, 주의 N건

## 🔴 FAIL
| 항목 | 기대값 (출처) | 실제값 (라인) |
   → 조치: <무엇을 해야 하는지 한 줄>

## 🟡 주의
   기획서 지시와 다르지만 의도된 변경일 수 있는 것. 근거 함께.

## ✅ PASS
   Phase 1 스크립트 결과 요약 + Phase 2 항목별 통과 건수.
   개별 나열은 특기할 것만.

## ⚪️ UNVERIFIED
   확인 못 한 항목 + **왜 확인 못 했는지 이유**.
   이유 없는 UNVERIFIED는 리포트 불량이다.

## 참고 — 이전 달 상속 이슈
   이번 달 회귀가 아닌 기존 문제. 판정 없이 기록만.
```

---

## 리포트 제출 전 자문 4가지

1. PASS로 쓴 항목 전부, 실제로 명령을 실행한 결과가 있는가?
2. 기획서 문자열을 내 말로 바꿔 적은 데가 있는가?
3. 정책 숫자(포인트·퍼센트·금액) 검사를 돌렸는가?
4. UNVERIFIED에 이유를 다 적었는가?

하나라도 아니오면 제출하지 않는다.
