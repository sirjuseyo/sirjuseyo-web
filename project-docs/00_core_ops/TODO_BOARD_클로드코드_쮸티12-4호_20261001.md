## ⚠️ 깃 운영 정책

### 작업 시작 전 코드 레포 원격 최신화 정책

- 작업 시작 전에는 항상 로컬 워크스페이스의 코드 레포 원격 상태를 확인한다.
- `project-docs`는 pull/merge/rebase 금지 대상이다. 문서 레포는 작성/커밋/푸시만 수행한다.
- 코드 레포는 `git fetch origin --prune`으로 원격 상태를 먼저 확인한다.
- 작업 대상이 될 가능성이 있는 코드 레포는 로컬 `dev`를 `origin/dev` 기준으로 맞춘 뒤 작업한다.
- 단, 로컬 변경/충돌/분기 상태가 있으면 임의로 merge/rebase/pull 하지 않고 먼저 보고한다.
- 최신화는 fast-forward 가능한 미반영 커밋만 반영하는 것을 원칙으로 한다.
- feature 작업 브랜치는 최신화된 `origin/dev` 기준으로 새로 만든다.
- 이후 순서는 로컬 컴파일/빌드 → 로컬 커밋 → 원격 feature 브랜치 푸시 → Open PR 생성 → 깃 관리자 전달 메시지 작성으로 진행한다.

### ⚠️ 작업 요청서 3단계 원칙 (DEV머지 → DEV preview → PRD, 뼈대·골격 — 2026-08-29 최종 확정 v2)

> ⚠️ v1(같은 날 오전 작성)은 틀렸음. "1차 요청서 = feature->dev 머지 + DEV preview를 하나로 묶어서"라고 썼는데, 실제로 T-156~163 1차 요청서를 그렇게 안 쓰고 "feature -> dev 검토 부탁드립니다"만 썼다가 실제로 PR #17이 `dev`에만 머지되고 `https://www.sirjuseyo.com/index-dev.html`에는 반영이 안 되는 사고가 났음. 깃 & 배포 관리자와의 실제 대화로 아래 표·원칙을 v2로 최종 확정.

**핵심 개념표 — `sirjuseyoWeb`(GitHub Pages 정적 사이트) 전용**

| 구분 | 의미 |
|---|---|
| 결과물 DEV 버전 | `index-dev.html`, `apply-dev.html`, `menu-dev.js` 등 테스트용 파일 |
| 결과물 PRD 버전 | `index.html`, `apply.html`, `menu.js` 등 운영용 파일 |
| 레포 `dev` | 개발 변경 이력을 모으는 브랜치. **소스 관리용일 뿐, 라이브 아님** |
| 레포 `main` | GitHub Pages가 **실제로 서빙하는** 유일한 브랜치 |
| 라이브 DEV | `main`에 올라간 `*-dev.html` 등 파일 (`www.sirjuseyo.com/index-dev.html`) |
| 라이브 PRD | `main`에 올라간 운영 파일 (`www.sirjuseyo.com/` 등) |

**절대 원칙: 레포 `dev`와 라이브 DEV는 다르다.** `feature -> dev` 머지는 소스 관리일 뿐이고, 그 자체로는 `www.sirjuseyo.com/index-dev.html`이 바뀌지 않는다. **라이브는 DEV든 PRD든 전부 `main` 기준**이다.

**3단계 요청서 (반드시 이 순서, 절대 건너뛰기 금지)**

1. **DEV 반영 요청서** — `feature -> dev` PR 머지만 요청 (소스 관리)
2. **DEV preview 배포 요청서** — `dev`에 반영된 것 중 DEV 테스트에 필요한 파일만 `main`에 **선별 반영**(전체 `dev->main` 머지 아님). PRD 운영 파일은 건드리지 않음. 이게 있어야 `www.sirjuseyo.com/index-dev.html`이 실제로 바뀜.
3. **PRD 운영 배포 요청서** — 댄디어빠쮸너야님이 DEV preview 라이브 URL에서 테스트 완료한 **후에만** 작성. PRD 대상 파일만 `main`에 선별 반영, `dev`↔`main` diverged 여부 확인 후 전체 병합 금지.

**1번+2번을 반드시 한 요청서에 같이 쓸지, 별도로 쓸지는 상황에 따라 다를 수 있으나 — 2번(DEV preview 파일을 main에 선별 반영)을 빠뜨리면 절대 안 된다.** 이번 T-156~163 사고가 정확히 이 누락이었음.

**DEV preview 요청서에 반드시 명시할 항목:**
- DEV 테스트 대상 파일 목록 (예: `index-dev.html`, `monthly-loan/{월}/index-dev.html`, `apply-dev.html`, `menu-dev.js`, 검사기 `index-dev.html`)
- **DEV/PRD 공유 파일**도 포함 (예: `tip/loan-checker/app.js`, `month-config.js` — DEV/PRD 양쪽 페이지가 같이 참조하므로 DEV 테스트에도 필요)
- **이미지 등 정적 자산**도 포함 (DEV·PRD 페이지가 같은 경로를 참조하는 경우 공통 반영 대상)
- DEV preview 확인 URL (예: `https://www.sirjuseyo.com/index-dev.html`)
- "PRD 운영 파일은 반영하지 말 것" 명시 + PRD 파일 목록을 "주의" 섹션으로 별도 나열
- "PRD 배포는 대표님 DEV 테스트 완료 후 별도 요청" 명시

**4축 관련:** `sirjuseyoWeb`은 서버가 아니라 정적 GitHub Pages라서 ECR/ArgoCD/Kubernetes는 항상 "대상 없음". DevOps/GitOps만 "GitHub PR `feature -> dev` merge 확인"으로 기재.

**완료 보고서 형식 (깃 관리자 → 개발자, 참고용):**
```
[DEV : 깃 & 배포 관리자 -> 개발자]
- feature -> dev 머지 완료
- DEV preview용 파일 main 선별 반영 완료
- DEV 라이브 URL 확인
- PRD 운영 파일은 미반영
```
```
[GitHub Pages PRD : 깃 & 배포 관리자 -> 개발자]
- DEV 테스트 완료 요청서 기준
- PRD 운영 파일 main 선별 반영 완료
- GitHub Pages 운영 URL 확인
```

**절대 금지:** ①1차 요청서에 "feature → main 검토 부탁드립니다"처럼 처음부터 PRD/main을 언급하는 것 ②DEV preview(main 선별 반영) 단계를 빠뜨리고 "feature->dev 머지만 요청 후 대표님께 라이브 DEV URL 확인해보라고 안내"하는 것.

## ⚠️ T-ID 커밋 해시 표기 준수사항 (뼈대·골격 — 2026-08-28 확정)

- 로컬 커밋은 원격 feature 브랜치 푸시 시 **회차(WT-ID 1차/2차/3차…) 구분 없이 전부 그대로 원격에 올라간다.** 즉, WT-ID의 각 회차마다 생성된 커밋 해시는 전부 원격 피처 브랜치 히스토리에 남는다.
- 따라서 투두 목록의 **"최종 해시" 컬럼에는 마지막 커밋 하나만 적지 않는다.** 해당 T-ID에 연동된 WT-ID 전체 회차의 커밋 해시를 **전부 나열**한다.
- 표기 형식: `1차 {해시} · 2차 {해시} · 3차 {해시} …`
- **이유:** 원격에는 회차별 커밋이 모두 남기 때문에, 투두 목록만 봐도 그 T-ID 작업에서 몇 번의 수정이 있었고 각 시점 코드가 무엇이었는지 인수인계 시 바로 추적 가능해야 함. 최종 해시 하나만 적으면 중간 회차 커밋이 왜 존재하는지 투두 목록만으로는 알 수 없게 됨.
- 워크스루(WORK_THROUGH)의 WT-ID 회차 테이블(각 회차별 커밋 해시 기록)과 TODO_BOARD 투두 목록의 이 컬럼은 **항상 1:1로 일치**해야 한다.
