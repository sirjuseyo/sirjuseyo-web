### ⚠️ 미해결 리스크 — 배포 후 검증 필요

**GitHub Pages가 확장자 없는 파일을 `application/octet-stream`으로 서빙한다.** 우리 사이트의 `CNAME` 파일로 실측 확인했다. Apple 요구사항은 `application/json`이라 **불일치**이며, GitHub Pages는 정적 호스팅이라 Content-Type을 바꿀 수 없다.

- **영향 범위는 iOS 한정.** Android는 AASA를 쓰지 않는다(스킴만 사용)
- 최악의 경우에도 Universal Link만 실패하고 **스킴 → 스토어 fallback이 동작**하므로 링크 자체는 살아 있음
- 차이는 "앱 미설치 아이폰에서 *주소를 열 수 없습니다* 팝업이 한 번 뜨느냐" 수준
- `.well-known/` 디렉터리가 Pages에 배포되는지도 **실배포 후 확인 필요**(`.nojekyll`이 있어 배포될 것으로 보나 확언하지 않음)

### 증상 (문제 설명)

iOS 클라(Ser10-3호)가 2026-10-06 회신에서 두 가지를 짚었다.

1. **Content-Type 리스크는 과대평가** — Apple은 AASA의 Content-Type을 검사하지 않음
2. **`.well-known/` 배포 여부가 더 위험** — 루트에도 함께 올리면 안전

### 원인 — 내 판단 오류

나는 `CNAME` 파일로 GitHub Pages가 `application/octet-stream`을 내보내는 것을 실측한 뒤, Apple 공식 문서의 `application/json` 요구사항과 대조해 **"iOS Universal Link가 안 될 수도 있다"**고 보고했다.

**실측 자체는 정확했으나 해석이 과했다.** iOS 회신에 따르면

- iOS 9 초기에는 서명된 파일(`application/pkcs7-mime`)을 요구했으나
- **iOS 10부터 평문 JSON을 받으면서 Content-Type 검사가 빠졌고**
- 현재 Apple 문서 요구사항은 **"확장자 없이 · 리다이렉트 없이 · HTTPS"** 뿐이다

GitHub Pages에 AASA를 올려 Universal Link를 쓰는 사례가 많다는 점도 지적받았다.

> 교훈: **"공식 문서에 A라고 적혀 있다"와 "A가 아니면 실패한다"는 다르다.** 실측값을 근거로 리스크를 제기한 것까지는 맞았지만, 그것이 실제 차단 요인인지는 확인하지 않고 "안 될 수도 있다"로 보고했다. 도메인 전문가(iOS 담당)의 검토를 받기 전까지는 **"확인이 필요한 불일치"** 수준으로 표현했어야 한다.

### 진단 (수정 이유)

**진짜 리스크는 `.well-known/` 디렉터리 배포 여부다.**

Jekyll은 점(`.`)으로 시작하는 디렉터리를 배포에서 제외하는 동작이 있다. 우리 레포에 `.nojekyll`이 있어 Jekyll 처리 자체가 비활성이므로 배포될 것으로 보이나, **실배포 전에는 확언할 수 없다.**

iOS 권고대로 **Apple의 탐색 순서**를 활용한다.

```
① https://www.sirjuseyo.com/.well-known/apple-app-site-association   ← 먼저 봄
② https://www.sirjuseyo.com/apple-app-site-association               ← 없으면 여기
```

둘 다 올리면 `.well-known/`이 배포에서 누락돼도 루트가 받아준다.

### 처방 (수정 코드)

